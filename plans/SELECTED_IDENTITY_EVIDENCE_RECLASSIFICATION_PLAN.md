# Plan: Selected Identity Evidence Reclassification

> Source: July 2026 selected-identity replay provenance review. The review found
> that deterministic selected-identity replay is identity wiring/accounting
> evidence, not model-based testing by itself, while current names and file
> placement make it easy to over-credit as MBT/QNT conformance.

## Problem

The repository currently uses `selected-identity-mbt`,
`UNIT-IDENTITY-MBT-REPLAY`, `*.mbt.test.ts`, `*.mbt.qnt`, and labels such as
`replays MBT parity` for selected-identity evidence that actually contains two
different claims:

- deterministic selected-identity replay: a TS/runtime wiring witness proving a
  claimed Unit id and named action reach the expected production boundary and
  projection;
- QNT parity replay: a `quint-connect run(...)` check against a focused QNT
  driver.

That mixed interface creates two risks. First, bookkeeping/wiring checks are
hidden in the scarce MBT lane because package `test` scripts exclude
`**/*.mbt.test.ts`. Second, humans and agents can reasonably infer that
deterministic selected-identity replay is MBT or cleanroom conformance evidence
because the machine vocabulary says MBT even where the semantic claim is only
identity wiring.

## Target Model

Use distinct evidence kinds everywhere the distinction matters:

- **Selected identity replay**: bookkeeping/wiring evidence. It proves concrete
  authored Unit identity, selected action names, production entrypoint
  reachability, and expected projection. It is normal test evidence, not MBT.
- **Deterministic QNT replay**: closed-case QNT replay through the QNT harness.
  It may be parity evidence when it executes QNT via `run(...)` and compares
  projection/state, but it is not random/generative MBT.
- **Focused MBT**: model-based testing through a QNT driver with generated traces
  or branches and state checks.
- **Cleanroom target replay**: stricter cross-language evidence generated by the
  target harness, with source hashes, branch/action identity, observed
  `actionTaken`, trace/seed, projection/state check, and pass/fail result.

The refactor must preserve all existing executable reachability guarantees. It
should change the interface so the wrong interpretation is difficult to make,
not merely add another warning paragraph.

## Phase 1: Rename the Evidence Vocabulary

**Goal**: Make the public accounting language match the actual claim before
moving files.

### What to build

Introduce explicit selected-identity replay vocabulary in the unit-profile
coverage model. Treat old `selected-identity-mbt` and
`UNIT-IDENTITY-MBT-REPLAY` names as legacy aliases only during migration.
Generated reports and checker messages should render the new terms.

Recommended durable names:

- evidence tag: `selected-identity-replay`
- marker: `UNIT-IDENTITY-REPLAY`
- report label: `Selected identity replay coverage`
- helper concept: selected identity replay witness

### Acceptance

- [ ] Unit-profile docs define selected identity replay as wiring/accounting
      evidence and explicitly exclude it from MBT, focused MBT, and cleanroom
      target replay by itself.
- [ ] Coverage config, validation messages, and generated reports use the new
      vocabulary for current output.
- [ ] Legacy names remain readable long enough for an incremental migration, but
      new uses are either rejected or reported as deprecated.
- [ ] No checker loses the existing requirements for replay data, declared
      actions, matching markers, QNT step reachability where still applicable,
      and production entrypoint reachability.

## Phase 2: Split Wiring Replay from QNT Parity

**Goal**: Put deterministic selected-identity replay in the normal test lane and
reserve `.mbt.*` paths for actual QNT/MBT parity.

### What to build

Create a two-owner evidence shape:

- a normal `.test.ts` owner for selected-identity replay data and deterministic
  runtime wiring assertions;
- a `.mbt.test.ts` owner for the QNT `run(...)` parity check when the Unit also
  has a focused QNT replay obligation.

The scanner should join these two owners through stable task id, Unit id, and
action names rather than requiring both claims to live in the same file.

### Acceptance

- [ ] Deterministic selected-identity replay checks run under ordinary package
      `pnpm test` lanes.
- [ ] QNT parity checks remain in explicit `.mbt.test.ts` lanes and keep the
      existing MBT scarcity rules.
- [ ] The scanner accepts split owners and rejects incomplete joins.
- [ ] Existing hand-rolled and helper-based selected-identity owners can migrate
      incrementally without weakening coverage.
- [ ] No selected-identity deterministic replay test title or describe label
      claims MBT.

## Phase 3: Rework Helper Interfaces

**Goal**: Make helper names and call sites encode the evidence kind.

### What to build

Replace the current all-in-one selected-identity helper interface with an
interface that makes the split explicit. The helper should no longer make a
single call site look like one MBT artifact when it creates both a deterministic
runtime witness and a QNT parity replay.

Possible shape:

- `defineSelectedIdentityReplayWitness(...)` for the deterministic runtime
  wiring/accounting test;
- `defineSelectedIdentityQntReplay(...)` or an equivalent parity helper for the
  QNT `run(...)` test;
- a shared typed data object only if it is the single source of truth for task
  id, Unit id, action names, and projections.

### Acceptance

- [ ] Helper names, test labels, and call-site fields distinguish selected
      identity replay from QNT parity.
- [ ] The deterministic helper does not import or imply QNT/MBT machinery.
- [ ] The parity helper requires a QNT spec path and calls `run(...)`.
- [ ] Shared replay data is represented once or generated from one source so
      action/projection drift cannot be represented silently.

## Phase 4: Enforce Lane and Naming Hygiene

**Goal**: Prevent the same confusion from reappearing after migration.

### What to build

Add executable checks that reject misleading evidence labels and file placement.
This is the main defense against future agent overclaiming; prose in AGENTS.md
is backup only.

Checks should cover:

- no selected-identity deterministic replay owner path ending in `.mbt.test.ts`;
- no selected-identity deterministic replay describe/test label containing
  `MBT`;
- no new `selected-identity-mbt` or `UNIT-IDENTITY-MBT-REPLAY` markers outside
  the legacy allowlist;
- no report column or generated status that groups deterministic replay under
  MBT completion;
- no rules-kernel aggregation that collapses deterministic QNT replay and
  focused MBT without preserving their distinct labels.

### Acceptance

- [ ] `pnpm quality` fails on new misleading selected-identity MBT vocabulary.
- [ ] Report output has separate labels for selected identity replay,
      deterministic QNT replay, and focused MBT.
- [ ] Existing migrated files do not need local comments to explain that they are
      not MBT; the names and checker output say it.

## Phase 5: Update Documentation and Generated Artifacts

**Goal**: Make docs, reports, and scaffolds tell the same story as the code.

### What to build

Update policy docs, generated coverage reports, cleanroom scaffold guidance, and
older PRD language so they use the target model consistently.

The docs should preserve two hard distinctions:

- selected identity replay is required wiring/accounting evidence for supported
  Unit identities;
- cleanroom target replay and focused MBT remain stricter evidence kinds and are
  never satisfied by selected-identity replay alone.

### Acceptance

- [ ] Unit-profile coverage docs use the new vocabulary as the primary term and
      describe old names only as migration aliases.
- [ ] Generated reports no longer say selected identities have MBT evidence when
      they only have selected-identity replay evidence.
- [ ] Cleanroom docs explicitly classify selected-identity replay as diagnostic
      or source/accounting evidence unless paired with harness-generated target
      replay evidence.
- [ ] Older PRD language is either updated or marked historical where it still
      says "Specific Unit Parity MBT" for selected-identity bookkeeping.

## Phase 6: Migrate Representative Owners, Then Batch

**Goal**: Prove the new model on a small set before migrating the corpus.

### What to build

Start with a representative vertical slice that includes:

- one helper-based battle-runtime selected-identity owner;
- one hand-rolled selected-identity owner;
- one non-battle runtime selected-identity owner;
- one selected identity that also has cleanroom route replay evidence.

After the scanner and docs are stable, migrate the remaining selected-identity
owners mechanically in batches.

### Acceptance

- [ ] The representative slice keeps unit-profile coverage green.
- [ ] Normal package tests run the deterministic selected-identity replay checks.
- [ ] Focused MBT commands still run the QNT parity tests.
- [ ] No cleanroom target replay evidence is downgraded or replaced by
      selected-identity replay.
- [ ] Batch migration can be reviewed mostly as mechanical renames/splits after
      the first slice lands.

## Verification

Run verification in this order for each implementation slice:

1. `pnpm unit-profile-coverage:check:self-test`
2. `pnpm unit-profile-coverage:check`
3. package `pnpm test` for every package whose selected-identity replay files
   moved into the ordinary test lane
4. focused MBT only for the QNT parity files changed by the slice
5. `pnpm rules-kernel-coverage:check` when witness-kind/report grouping changes
6. `pnpm cleanroom-branch-coverage:check` and cleanroom scaffold checks when
   target replay docs/templates are touched
7. `pnpm quality` before merging a completed slice

Reviewer-loop convergence applies after non-mechanical changes. Run RAW,
ubiquitous-language/domain, architecture/connascence, and code-review passes;
fix reasonable findings and repeat until no reasonable findings remain.

## Non-Goals

- Do not remove selected-identity replay evidence.
- Do not weaken production entrypoint reachability checks.
- Do not count selected-identity replay as cleanroom target replay.
- Do not run broad MBT as a migration discovery mechanism.
- Do not solve every historical naming issue in one mechanical mega-commit if a
  staged alias period keeps quality gates meaningful.

## Open Decisions

- Whether legacy `selected-identity-mbt` rows should be rewritten in one
  generated-data commit or accepted through a time-boxed compatibility alias.
- Whether selected-identity QNT files should use a `.replay.qnt` suffix or keep
  `.mbt.qnt` only for QNT parity owners during the transition.
- Whether split owners should share a generated replay manifest or import a
  typed local replay-data module.
