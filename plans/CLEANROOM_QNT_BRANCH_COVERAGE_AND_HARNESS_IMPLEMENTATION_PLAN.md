# Plan: Cleanroom QNT Branch Coverage And Harness

> Source PRD: `plans/PRD_CLEANROOM_QNT_BRANCH_COVERAGE_AND_HARNESS.md`

## Architectural Decisions

Durable decisions that apply across all phases:

- **QNT role**: QNT remains the formal conformance source. Branch coverage
  artifacts are checker and harness metadata over Quint MBT traces, not new
  rule semantics.
- **Branch denominator**: an in-scope branch is a named leaf action that Quint
  can report through `mbt::actionTaken` under a cleanroom-facing `step` action
  or declared branch family.
- **Sampled inputs**: `nondet` values are sampled input variation and live in
  `sampledInputs`, not in the branch denominator.
- **Source readiness artifact**: `sourceBranchInventory` records discovered
  branch obligations, QNT file hashes, scope, replayability, and source
  blockers or exemptions.
- **Target acceptance artifact**: `targetReplayEvidence` is generated by a
  target harness after actual QNT/MBT replay. Validation-report prose and
  focused target-language tests cannot close branch coverage.
- **Scope curation**: source branch discovery is generated from QNT source; only
  branch scope, blocker, exemption, and replay-rationale decisions are curated.
- **Scaffold target shape**: target-specific commands, extensions, path
  conventions, and Quint binding details come from a target profile.
- **Cleanroom boundary**: generated cleanroom inputs may include RAW, QNT,
  domain language, curated assumptions, branch inventory, guidance pack,
  scaffold, and target profile. They must not include production
  implementation code, production tests, prior cleanroom output, or uncontrolled
  planning logs.
- **Acceptance loop**: every cleanroom task is accepted by deterministic gates
  plus recorded reviewer-loop convergence, not by implementer report prose.

## Phase 1: Branch Contract Tracer Bullet

**User stories**: 1-14, 23-24

### What to build

Build the smallest source-side branch coverage contract that can prove the
shape end to end: discover branch actions from `.mbt.qnt` drivers, separate
branch obligations from sampled `nondet` inputs, validate curated scope rows,
validate target replay evidence rows, and render a generated coverage table.

Start with synthetic checker fixtures and one real cleanroom-facing driver so
the contract is executable without hardening the full corpus yet.

### Tasks

- [x] Define the `sourceBranchInventory` JSON shape with `branchObligations[]`
  and `sampledInputs[]`.
- [x] Define the `targetReplayEvidence` JSON shape for harness-generated branch
  receipts.
- [x] Add a source checker that parses QNT driver action families and discovers
  named leaf branch actions.
- [x] Add source checker validation for stale hashes, missing scope rows,
  missing replayability, missing blockers, and stale/manual coverage rows.
- [x] Add target evidence validation keyed by manifest SHA, QNT file hash,
  branch action, observed `mbt::actionTaken`, harness path, and pass/fail
  result.
- [x] Render a generated branch coverage table that distinguishes target
  QNT/MBT replay from diagnostic target-language unit tests.
- [x] Add self-tests with fixture QNT drivers covering one-branch, multi-branch
  `any {}`, nested branch-family, sampled-input, blocker, and stale-evidence
  cases.

### Acceptance Criteria

- [x] A new branch action in a scoped cleanroom-facing driver fails the source
  checker until it has inventory scope and replayability metadata.
- [x] A sampled `nondet` value is recorded as sampled input and does not expand
  the branch denominator.
- [x] Target evidence fails if `observedActionTaken` differs from the expected
  branch action.
- [x] Target evidence fails if it is keyed to a stale QNT file hash or stale
  cleanroom manifest.
- [x] Validation-report prose cannot mark an uncovered branch as covered.
- [x] The checker self-test is cheap and does not run MBT.

## Phase 2: Cleanroom Scaffold Generalization

**User stories**: 15-18, 34-36

### What to build

Turn the current Rust-specific cleanroom scaffolds into language-independent
templates driven by target profiles. The generated cleanroom instructions
should tell a future target implementer how to consume source branch inventory,
emit target replay evidence, quarantine driver adapters, and treat focused unit
tests as diagnostics only.

### Tasks

- [x] Define a target-profile schema for package manager, formatter, compiler,
  linter, test command, file extensions, path conventions, and Quint binding.
- [x] Update cleanroom templates so target-specific strings come only from the
  target profile.
- [x] Update work-loop instructions to require source branch inventory and
  harness-generated target replay evidence for selected drivers.
- [x] Update validation-report templates so the branch coverage table is
  generated from target replay evidence.
- [x] Update blocker templates so source QNT blockers and target implementation
  blockers are recorded separately.
- [x] Add dry-run rendering checks for at least two synthetic target profiles
  with different command and path conventions.

### Acceptance Criteria

- [x] The scaffold can render for two distinct target profiles without
  hard-coded Rust assumptions outside profile data.
- [x] A rendered cleanroom report cannot claim focused unit tests close MBT
  branch coverage.
- [x] The cleanroom work loop requires target replay evidence before accepting
  a branch as conformant.
- [x] The generated bootstrap manifest records allowed roots, source hashes,
  and denied prior-cleanroom inputs.

## Phase 3: Harness Acceptance Gates

**User stories**: 19-26

### What to build

Add the Ralph-style implementer, reviewer, handback, and decider harness
contracts around the cleanroom scaffold. Acceptance should require deterministic
gates for branch coverage, adapter quarantine, engine depth,
state-owner/derivability, authored-identity dispatch, report honesty, and
reviewer-loop convergence.

### Tasks

- [x] Add implementer task instructions that require declared Base SHA, `HEAD`,
  and ancestor check before work starts.
- [x] Add reviewer templates for RAW/QNT traceability, domain architecture,
  branch coverage, code shape, adapter quarantine, engine depth, state
  ownership, and authored-identity dispatch.
- [x] Add a decider checklist that accepts only passing deterministic gates plus
  fixed or explicitly rejected reviewer findings.
- [x] Define the engine-depth manifest shape for production modules extended,
  domain API introduced or reused, adapter modules touched, quarantined witness
  names, and expected next reuse.
- [x] Define the state-owner/derivability manifest shape for every durable field
  introduced by a cleanroom task.
- [x] Add synthetic fixture checks for adapter leakage, public witness-surface
  leakage, large accumulator growth, missing engine-depth manifest rows,
  redundant state, authored-identity dispatch, and report dishonesty.

### Acceptance Criteria

- [x] A task with uncovered in-scope MBT branches cannot be accepted.
- [x] A task with stale or missing Base SHA ancestor check cannot start.
- [x] A task with unresolved reasonable reviewer findings cannot be accepted.
- [x] Public production symbols derived from witness protocol names are
  rejected or require a documented adapter boundary.
- [x] Durable target fields without an owner and derivability classification are
  rejected.

## Phase 4: Character-Creation QNT Hardening

**User stories**: 27-30

### What to build

Harden character-creation QNT as the first rule-modeling source-side readiness
slice. The modeled contract is a current-frontier, atomic batch process:
discover current holes, validate a whole fill batch, reject without mutation,
accept atomically with one revision increment, rediscover holes, and finalize
only when the build boundary is complete and supported.

### Tasks

- [x] Read the relevant SRD 5.2.1 character-creation passages and
  `UBIQUITOUS_LANGUAGE.md` before changing QNT.
- [x] Identify current character-creation drivers and source branch inventory
  rows that are blocked by missing replayability or weak branch shape.
- [x] Add deterministic replay entrypoints or valid initializer actions for
  current-frontier, stale-revision, duplicate-fill, wrong-kind,
  unsupported-option, non-current-hole, and future-hole branches.
- [x] Preserve atomic rejection: original draft and original holes survive every
  rejected batch.
- [x] Preserve accepted batch semantics: exactly one revision increment, all
  accepted fills applied together, holes rediscovered from the new draft, and
  finalization status recomputed.
- [x] Model progression fill as one `CharacterProgression` selection so
  starting class and advancement entries cannot drift.
- [x] Update source branch inventory and package-local QNT/MBT tests for the
  hardened branches.

### Acceptance Criteria

- [x] Character-creation frontier and atomic-batch invariants are either
  QNT/MBT-covered or listed as blocking source readiness work.
- [x] Rejected fills cannot mutate draft state or open-hole state.
- [x] Accepted fills cannot partially apply a batch.
- [x] Finalization cannot succeed with open holes or unsupported selections.
- [x] Progression state cannot represent separate drifting starting-class and
  advancement facts.

## Phase 5: State Ownership Guidance Pack

**User stories**: 31-35

### What to build

Create the curated language-independent guidance pack that a future cleanroom
target can read without seeing production implementation code. It should capture
the domain architecture decisions needed to avoid witness accretion, redundant
state, authored-identity dispatch, and build/sheet/battle ownership drift.

### Tasks

- [ ] Curate guidance for the QNT forest and sibling harness architecture.
- [ ] Curate guidance for character-build ownership, including durable build
  evidence, selected Unit references, source-scoped spell choices,
  equipment/loadout, and allowed build-owned slot-pool evidence.
- [ ] Curate guidance for character-sheet ownership of mutable in-play state:
  current Hit Points, Hit Point maximum changes, spent Hit Dice, slots,
  resources, rest feature use, and related lifecycle facts.
- [ ] Curate guidance for battle ownership of encounter state and
  character-battle ownership of initialization and settlement projections.
- [ ] Curate guidance for support-profile admission, readers, typed procedure
  facts, provenance separation, no authored-identity dispatch, no redundant
  state, and invalid states made unrepresentable.
- [ ] Add allowlist-based guidance-pack generation or validation so production
  code, tests, prior cleanroom output, and uncontrolled planning logs cannot
  enter the cleanroom input.

### Acceptance Criteria

- [ ] Guidance pack includes the curated architecture findings needed by a fresh
  target implementer.
- [ ] Guidance pack excludes production implementation code and production
  tests.
- [ ] Guidance pack distinguishes provenance, structured input, runtime
  projection, build evidence, sheet state, battle state, and harness witness
  protocol.
- [ ] Cleanroom bootstrap fails if guidance inputs are unmanifested or denied.

## Phase 6: End-to-End Bootstrap Dry Run

**User stories**: all acceptance-oriented stories

### What to build

Run the full source-side readiness flow into a temporary cleanroom directory.
The dry run should prove the manifest, allowed inputs, branch inventory,
guidance pack, scaffold, target profile, validation report format, and harness
gates are self-consistent before a new target-language implementation starts.

### Tasks

- [ ] Generate a cleanroom input snapshot into a temporary directory.
- [ ] Include manifest, allowed source roots, source hashes, branch inventory,
  guidance pack, scaffold files, and at least one synthetic target profile.
- [ ] Run source branch inventory checks against the copied QNT corpus.
- [ ] Run scaffold rendering checks against two synthetic target profiles.
- [ ] Validate example target replay evidence for covered, uncovered, stale,
  wrong-action, diagnostic-only, and blocked branches.
- [ ] Validate reviewer-loop and decider records in a synthetic cleanroom task.
- [ ] Confirm prior cleanroom implementation output is denied and not accepted
  as evidence.

### Acceptance Criteria

- [ ] A fresh cleanroom task cannot be accepted unless every in-scope branch for
  its selected drivers has passing target QNT/MBT replay evidence.
- [ ] The bootstrap manifest, branch inventory, guidance pack, scaffold, and
  target profile are mutually consistent.
- [ ] The dry run proves stale hashes, unmanifested inputs, manual report rows,
  and diagnostic-only tests fail acceptance.
- [ ] The current cleanroom implementation is not used as acceptance evidence
  for the next experiment.

## Verification

- **Reviewer-loop convergence.** After implementation of each substantial
  phase, run RAW/QNT traceability, ubiquitous-language/domain,
  architecture/connascence, branch-coverage, and code-review passes. Fix every
  reasonable finding, explicitly reject only findings with a concrete reason,
  and repeat until no reasonable findings remain. The cleanroom harness must
  record this loop after each accepted milestone.
- **RAW/ubiquitous-language check.** Before changing or adding rule-modeling
  QNT, read the relevant SRD 5.2.1 passage in `.references/srd-5.2.1/` and
  check `UBIQUITOUS_LANGUAGE.md`. Verification must confirm that modeled rules
  trace to specific SRD text and that domain names match the repo vocabulary.
- Run source checker suites for branch discovery, source branch inventory,
  target replay evidence, report claims, and scaffold rendering.
- Run package-local QNT/MBT lanes affected by any QNT driver or
  character-creation change. Use the repo MBT scarcity protocol for every MBT
  run.
- Run existing QNT closure and import-budget checks so deterministic branch
  entrypoints do not weaken MBT performance discipline.
- Dry-run cleanroom sync/bootstrap into a temporary directory and validate the
  manifest, allowed inputs, guidance pack, scaffold, target profiles, branch
  inventory, target evidence, and report gates.
