## Surface Package Decision

Recommend using `@dnd/surface` directly as the active package, not creating a facade.

Reason: the existing package already owns the Surface schemas, `UnitRecord` union, decode helpers, structural vocabulary, and authored SRD content directory. A facade would create a second package boundary before the green runtime has stabilized, and it would make imports ambiguous between "prototype" and "real" Surface. This is a greenfield stack with no external consumers, so preserving the old package name has no compatibility value.

Package/import consequences:

- Rename package directory or package name to `@dnd/surface`.
- Runtime packages import schemas, types, and decode helpers from `@dnd/surface`.
- Update repo docs to refer to `@dnd/surface` as the active package; historical prototype-package references should be explicitly archival or removed.
- Keep authored SRD content either in this package during Phase 1 or move it behind a later `@dnd/srd-units` artifact without changing Surface type imports.
- Deleted `packages/surface-runtime-correction` patterns may be read from git
  history as source material when they are reused.
- Do not introduce `@dnd/surface-runtime-*` package-specific content languages.

## Unit Library Boundary

Minimum API:

```ts
type UnitId = Brand<string, "UnitId">;
type UnitCollectionId = Brand<string, "UnitCollectionId">;

type SourcedUnitRecord = SrdUnitRecord | PrivateUnitRecord;

type SrdUnitCollection = {
  readonly id: UnitCollectionId;
  readonly provenance: SrdProvenance;
  readonly distribution: UnitCollectionDistribution;
  readonly units: readonly SrdUnitRecord[];
};

type PrivateUnitCollection = {
  readonly id: UnitCollectionId;
  readonly provenance: PrivateProvenance;
  readonly distribution: UnitCollectionDistribution;
  readonly units: readonly PrivateUnitRecord[];
};

type UnitCollection = SrdUnitCollection | PrivateUnitCollection;

type UnitLibrary = {
  readonly collections: readonly UnitCollection[];
  readonly unitsById: ReadonlyMap<UnitId, SourcedUnitRecord>;
  readonly getUnit: (id: UnitId) => SourcedUnitRecord | undefined;
};

function buildUnitLibrary(input: {
  readonly collections: readonly UnitCollection[];
}): UnitLibrary;
```

Duplicate id policy: reject duplicate `UnitRecord.id` across the whole library for Phase 1. Namespacing can be designed later if private collections need overrides, but no implicit shadowing should exist now.

Collection provenance policy: the collection union must make every unit share the same provenance variant as the collection. `SrdUnitCollection` must accept only `SrdUnitRecord`s with `provenance.kind === "srd-5.2.1"`. A mixed SRD/licensed collection should be unconstructable through the public builder and rejected by runtime validation if malformed JSON bypasses TypeScript. Library lookup preserves the sourced record; runtime semantic readers may narrow to structural views, but package APIs must not discard provenance.

Composition policy:

- App/MCP composition installs `srdUnitCollection` with `buildUnitLibrary({ collections: [srdUnitCollection] })`.
- Future private/licensed collections install beside SRD at the composition root: `buildUnitLibrary({ collections: [srdUnitCollection, privateUnitCollection] })`.
- Runtime semantics branch on decoded Surface structure, not provenance. Provenance is for legal/source boundary control and auditability.
- Phase 1 can keep `srdUnitCollection` close to MCP/app composition if package churn is a concern, but it must be a real import before reducer implementation. Create `@dnd/srd-units` only when imports or distribution policy force it.

## Monster/Stat Block Boundary

Represent the first monster, Goblin Warrior, as a distinct authored Stat Block record, not as `UnitRecord`.

The record type must be generic. The SRD-specific part belongs to the collection/provenance value, not to the runtime-facing record name.

Recommended type:

```ts
type StatBlockRecord = {
  readonly id: string;
  readonly kind: "stat_block";
  readonly name: string;
  readonly provenance: Provenance;
  readonly statBlock: CreatureStatBlock;
};
```

Why this is not a character draft: it is authored rules content, immutable after decode, and comes directly from the SRD monster corpus. A character draft is session-owned evolving user input.

Why this is not a Core catalog import: the promoted runtime path must not read `@dnd/core` monster catalogs. The SRD Goblin Warrior record should decode against `@dnd/surface` stat-block schema or a sibling stat-block schema owned by `@dnd/surface`.

Why not `UnitRecord`: current `UnitRecord` variants describe spells, features, feats, species traits, magic items, armor, shields, weapons, templates, and masteries. A full monster Stat Block is a separate SRD domain boundary in `UBIQUITOUS_LANGUAGE.md`, and forcing it into `UnitRecord` would conflate executable unit mechanics with authored creature records. Surface already has `CreatureStatBlockSchema`; expose it as a first-class authored record boundary instead.

Collection policy: `srdStatBlockCollection` should have the same single-provenance collection invariant as Unit collections and should contain only `StatBlockRecord`s whose provenance is SRD 5.2.1, but it should not be mixed into `buildUnitLibrary`. Battle composition can receive both `unitLibrary` and `statBlockCatalog`. A later private/licensed stat-block collection should use the same `StatBlockRecord` shape with a different collection/provenance boundary.

## No-IR Check

Rejected tempting intermediate representations:

- `CPU*`, `PEA*`, `PPR*`: must be deleted rather than preserved under cleaner names.
- `SupportedUnitLibrary` as semantic vocabulary: acceptable only as a local support gate in a reducer slice. Do not export it as the content language.
- `BattleReadyWeaponAttack`: acceptable only as a narrow runtime projection wrapper carrying selected equipment reference plus derived numeric facts. It must not duplicate the weapon damage expression independently of `WeaponRecord`.
- `FighterPreset` or `GoblinWarriorPreset`: rejected. The first vertical can have a fixture story, but creation must still flow through holes and decoded authored content.
- `ExecutableUnit`, `InterpretedUnit`, or `ResolvedUnitEffect`: rejected as exported or durable types. Local reducer reader results are allowed only when named after the structural invariant they prove, such as `WeaponAttackDamageReaderResult` or `ArmorClassContribution`, and scoped to the reducer module.
- `MonsterUnit`: rejected. Use generic `StatBlockRecord` / `CreatureStatBlockRecord` naming to preserve the Stat Block domain boundary; keep SRD in the collection/provenance boundary.
- `ProvenanceRuntimeKind`: rejected. Runtime semantics must branch on structural facts, not SRD/private provenance.

## Questions For Owner

1. Is `plans/phase1-fighter-manifest.md` accepted as the controlling manifest for the remaining Phase 0 audits?

   Recommended answer: yes. It is precise enough to drive package API design and keeps the green battle slice to one Fighter weapon attack plus runtime `endTurn`.

2. Should Phase 1 add `BackgroundRecord` and a minimal `background_soldier` UnitRecord variant now?

   Recommended answer: yes. Background is authored SRD content with legality consequences: ASI options, origin feat, proficiencies, and equipment. Keeping it as draft-only data would duplicate rules content in character creation.

3. Should Phase 1 add a Species aggregate record, or model Orc as separate `SpeciesTraitRecord`s plus draft-owned species identity?

   Recommended answer: add a minimal Species aggregate record. Orc's size, speed, creature type, and traits must be selected together; separate trait Units cannot make mixed-species states unrepresentable.

4. Should the first SRD Unit collection live in `@dnd/srd-units` immediately?

   Recommended answer: not yet. Keep SRD Units with `@dnd/surface` or MCP/app composition until runtime imports settle. Still implement `srdUnitCollection` as a real typed collection before reducer work.

5. Should the Goblin Warrior stat block collection be separate from `buildUnitLibrary`?

   Recommended answer: yes. Stat Blocks are authored content, but they are not Units. Use `buildStatBlockCatalog({ collections: [srdStatBlockCollection] })` with the same duplicate id and provenance policies. The catalog should return generic `StatBlockRecord`s; the SRD-specific fact is on the collection and provenance.

6. Are Longsword Sap and Goblin Warrior's Advantage rider intentionally out of the first battle semantics?

   Recommended answer: yes. The first attack needs ordinary Longsword hit/damage only. Author missing rider content if needed for sheet legality, but support-gate execution out unless the owner expands the green battle slice.
