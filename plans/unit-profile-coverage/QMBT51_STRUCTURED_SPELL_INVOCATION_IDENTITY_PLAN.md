# QMBT51 Structured Spell Invocation Identity Plan

Date: 2026-05-07

## Decision

Refactor promoted battle-runtime spell acts so runtime subjects and supported
spell invocations use structured domain identity instead of encoded
`spellActId` strings and access/resource/procedure-conflated variant names.

This task is architectural cleanup for the currently promoted spell lanes. It
does not widen spell behavior to magic-item charge casting, general granted
spells, broad at-will spell access, rituals, pact slots, or known-spell classes.

## Problem

Current `SupportedSpellAct` variants encode several domain facts into one tag:

- `preparedSlotSpell` combines prepared access, Spell Slot resource, and a
  repeated damage-allocation procedure.
- `preparedHealingSpell` combines prepared access, Spell Slot resource, Hit
  Point restoration procedure, and action-cost routing.
- `preparedPersistentSpell` and `preparedShieldReactionSpell` similarly mix
  prepared access, Spell Slot resource, and procedure.
- `cantripSpellAttack` and `cantripSaveGateDamage` use cantrip status as if it
  were the whole access/resource model.

The public/runtime subject path also carries `spellActId` as generic text. That
text is generated by `supportedSpellActId`, parsed by `startsWith`/`slice` for
readied spells, hard-coded in tests, and compared to regenerated strings during
stale-subject resolution. Branding that string would prevent accidental mixing
with arbitrary strings, but would preserve the real connascence.

The real boundary should represent:

- Spell Definition: the static authored `SpellRecord`.
- Spell Access: the creature-owned relationship to a spell definition.
- Spell Invocation: a concrete runtime cast option, including procedure and
  resource/cast level.
- Spell Effect: battle state created by resolving the invocation.

These terms already exist in `UBIQUITOUS_LANGUAGE.md` and should drive the
implementation names.

## Review Findings

Three review agents evaluated the proposal before this task was written.

Architecture review:

- Splitting spell acts into spell definition, procedure, access, resource, and
  action cost is sound.
- A loose product type would still represent invalid states, such as a cantrip
  with a Spell Slot resource. Use constrained unions or trusted constructors.
- Reuse existing `SpellSlotLevel` and `ResourceCount` before adding new numeric
  brands.
- Access source identity will probably be needed before duplicate class,
  species, feature, or item access can be supported without collisions.

Type/protocol review:

- `spellActId` should not remain the primary domain model. A branded encoded
  string would not fix `readiedSpell:` prefix coupling.
- Readied spell identity should be a structured subject mode, such as
  `{ tag: "cast" }` versus `{ tag: "ready"; trigger }`, while held readied
  spell state continues to live in `state.readiedSpells`.
- `BattleSubjectSchema` should parse structured spell refs instead of accepting
  loose `spellId`/`spellActId` text.
- If a display/replay key remains, derive it from the structured ref in one
  helper and never parse it.

RAW/spec review:

- The split is supported by SRD language and the repo's ubiquitous language.
- Item, charge-cast, broad limited-use, broad granted, and broad at-will spell
  behavior must remain out of scope until the battle projection carries real
  creature-owned access/resource data.
- Quint and MBT bridge changes are required because current tests and promoted
  spec projections hard-code mixed spell act IDs and slot behavior.

## Target Shape

Use structured invocation refs in subjects and tests:

```ts
type SpellInvocationRef =
  | {
      readonly tag: "cantrip";
      readonly spellId: SpellId;
      readonly procedure: "spellAttackDamage" | "saveGateDamage";
    }
  | {
      readonly tag: "spellSlot";
      readonly spellId: SpellId;
      readonly slotLevel: SpellSlotLevel;
      readonly procedure: SpellSlotProcedure;
    };

type SpellSubjectMode =
  | { readonly tag: "cast" }
  | { readonly tag: "ready"; readonly trigger: BattleReadiedSpellTrigger };
```

Use constrained runtime invocation unions, not independent optional fields:

```ts
type SupportedSpellInvocation =
  | {
      readonly access: { readonly tag: "prepared" };
      readonly resource: {
        readonly tag: "spellSlot";
        readonly slotLevel: SpellSlotLevel;
      };
      readonly procedure: SpellSlotProcedure;
    }
  | {
      readonly access: { readonly tag: "classCantrip" };
      readonly resource: { readonly tag: "none" };
      readonly procedure: CantripProcedure;
    };
```

Procedure names should describe execution shape, not access or resource:

- repeated damage allocation;
- spell attack damage;
- save-gated damage;
- persistent armor effect;
- shield reaction;
- direct Hit Point restoration.

Branding strategy:

- Add `SpellId` only where it removes raw-string ambiguity at a boundary.
- Reuse `SpellSlotLevel`, `ResourceCount`, `MovementFeet`, `MovementDeltaFeet`,
  `Hp`, `ProficiencyBonus`, and `CombatantId`.
- Consider a positive-count brand for repeated effect count and target count if
  those counts cross a runtime boundary.
- Leave closed vocabularies as literal unions: procedure tags, action tags,
  trigger tags, speed kinds, and damage types.

## Implementation Plan

1. Introduce structured spell invocation references.

   Add battle-runtime types and schemas for `SpellInvocationRef` and
   `SpellSubjectMode`. Update `BattleSubjectSchema` spell subjects to carry the
   structured ref and mode. Keep compatibility helpers only if needed for an
   internal migration, and remove encoded-string parsing before closeout.

2. Replace readied spell prefix semantics.

   Remove `readiedSpellActId`, `isReadiedSpellActId`, and
   `castSpellActIdFromReadied`. Ready spell discovery should emit a spell
   subject whose mode is `ready`. Resolution should branch on the parsed mode,
   not on string prefixes. Release should continue to use held readied spell
   state keyed by caster identity.

3. Reshape supported spell invocations.

   Rename `SupportedSpellAct` or introduce a replacement type whose variants
   constrain the current supported lanes:

   - prepared + Spell Slot + repeated damage allocation;
   - prepared + Spell Slot + direct Hit Point restoration;
   - prepared + Spell Slot + persistent armor effect;
   - prepared + Spell Slot + shield reaction;
   - class cantrip + no resource + spell attack damage;
   - class cantrip + no resource + save-gated damage.

   Do not model item charge casting, granted spell access, known spell classes,
   pact slots, rituals, or generic limited-use casting in this task.

4. Derive matching keys from structured refs.

   Replace `supportedSpellActId(invocation): string` with
   `supportedSpellInvocationRef(invocation): SpellInvocationRef` and explicit
   equality helpers. If UI/replay requires an opaque key, derive it one-way from
   the structured ref and avoid parsing it for behavior.

5. Update resource and action-cost helpers.

   Make helpers consume `resource` and `procedure/actionCost` instead of
   checking variant names such as `preparedHealingSpell`. Slot spending should
   dispatch from `resource.tag === "spellSlot"`. Bonus Action routing should
   dispatch from procedure action cost, not from a prepared/healing variant name.

6. Update Quint and MBT bridge expectations.

   Keep promoted behavior equivalent, but update `battle-runtime.qnt`, package
   local MBT projections, and deterministic tests so spell subjects and
   invocation identity use structured refs rather than encoded strings.

## Out of Scope

- Supporting magic-item charges or charge-cast spend.
- Supporting non-Wizard known-spell classes.
- Supporting pact slots.
- Supporting broad granted, innate, always-prepared, or at-will spell access
  beyond current cantrip behavior.
- Adding rituals.
- Widening spell catalog admission.
- Changing the semantics of Magic Missile, Ray of Frost, Acid Splash, Mage
  Armor, Shield, Healing Word, Cure Wounds, Mass Healing Word, or Mass Cure
  Wounds.

## Acceptance Criteria

- No behavior path parses `readiedSpell:` or any encoded spell act string.
- Spell subjects carry a structured invocation ref and mode.
- Supported spell invocation matching compares structured refs, not generated
  strings.
- Resource spend is driven by `resource`, and action-cost routing is driven by
  procedure/casting-time facts.
- Current promoted spell behavior remains equivalent for prepared slot spells,
  cantrips, bonus-action healing, Shield reaction, and Ready spell.
- Tests no longer infer slot level or readied state from `spellActId` string
  suffixes/prefixes.
